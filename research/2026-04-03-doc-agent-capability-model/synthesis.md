# 综合分析：文档能力模型 × Harness Engineering

日期：2026-04-03
基于 Track A（文档基础能力模型）和 Track B（Harness Engineering）的调研结果综合而成。

---

## 一、核心判断

当前系统的投入重心和实际需要之间存在错位：

| 维度 | 已投入 | 缺失 |
|------|--------|------|
| 流程支撑（phase、receipt、durable state） | 大量 | — |
| 文档质量模型（什么叫"好文档"） | 零 | **关键缺失** |
| 任务意图重建（用户说不清时怎么办） | 零 | **关键缺失** |
| 材料角色识别（不同源文件该怎么用） | 零 | **关键缺失** |
| 质量判断环路（写完后怎么知道好不好） | 结构检查 | **质量判断缺失** |
| 观察面设计（agent 看到什么） | 过程状态 | **能力放大型观察面缺失** |
| 场景泛化（不同文档类型的适配） | 有偏置 | **路由机制缺失** |

一句话：系统知道"怎么持续跑"，但不知道"什么叫写得好"。

## 三、四层架构提案

```
┌─────────────────────────────────────────────┐
│ Layer 3: 场景 Skill 层（按需加载）            │
│   标书写作、政策起草、技术文档、会议纪要、      │
│   研究报告、比较简报、正式信函…               │
│   每个 skill 只增加本场景的质量标准、          │
│   结构约定、术语和验证规则                    │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│ Layer 2: Harness 层（能力放大器）             │
│   任务建模 harness：意图重建 + 任务 schema     │
│   观察面 harness：草稿摘要、质量增量、         │
│       token 预算感知的 MCP 工具               │
│   动作面 harness：结构化门控 + 提交确认        │
│   质量判断 harness：评价器-优化器环路 +        │
│       基于评估维度的结构化反馈                 │
│   恢复 harness：decisions.json +              │
│       新鲜度追踪 + 恢复摘要                   │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│ Layer 1: 文档基础能力层（始终激活）            │
│   8 个质量维度（D1-D8）                       │
│   任务意图重建协议                            │
│   材料角色分类框架                            │
│   自适应流水线深度                            │
│   工作流能力：intake → evidence → compose →   │
│       verify（增强版）                        │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│ Layer 0: 工程支撑层（基础设施）               │
│   .worktree/ 持久状态                         │
│   session 管理                                │
│   phase routing                               │
│   错误恢复                                    │
│   workspace 边界                              │
└─────────────────────────────────────────────┘
```

**核心原则：**
- Layer 1 定义"什么是好文档"——这是用户感知到的核心
- Layer 2 让模型"更容易做到好"——这是 harness 的意义
- Layer 3 适配具体场景——不污染基础层
- Layer 0 保证系统跑得稳——已有较好基础

## 四、最高杠杆的 5 个变更

按照"对最终文档质量的影响力"排序，不是按实现难度排序。

### 变更 1：在 common-work.md 中植入文档质量模型

**为什么排第一：** 当前系统完全没有"什么叫好文档"的内化标准。agent 只知道"做完了没"，不知道"做好了没"。这是影响所有文档场景、所有任务类型的根本缺失。

**具体做法：**
- 在 common-work.md 中增加一个"文档质量维度"小节（约 20-30 行）
- 包含 8 个维度：目的对齐、受众校准、事实准确、结构完整、逻辑连贯、语言精确、源忠实、格式合规
- 每个维度一句话定义 + 一句话评估标准
- 在起草和验证环节都引用这些维度

**预期效果：** agent 在写作时有内在标准参照，在验证时不只检查结构而是评价质量。

### 变更 2：在 common-work.md 中增加任务意图重建协议

**为什么排第二：** 用户提问质量差是常态，不是例外。如果系统不能从模糊指令中重建合理的内部任务模型，后续再好的流程也是在执行一个错误目标。

**具体做法：**
- 增加"任务意图重建"小节（约 15-20 行）
- 当接到新文档任务时，agent 先推断：文档类型、受众、目的、范围、重点、语气、格式预期
- 以紧凑的"文档简报"形式向用户呈现推断结果（5-8 行）
- 用户确认或纠正后再开始工作
- 核心原则：先推断后声明，不是先问后做，也不是默默假设

**预期效果：** 即使用户只说"帮我写个总结"，系统也能产出一份面向正确受众、具有正确深度的文档。

### 变更 3：将 document-verify 从结构检查器升级为质量判断器

**为什么排第三：** 当前验证只检查"标题对不对、文件在不在、事实在不在"。一份通过所有结构检查但论证松散、受众错位、语言空泛的文档，在当前系统中会被宣告"完成"。

**具体做法：**
- 重写 document-verify SKILL.md
- 分两步：结构验证（快速、可自动化）+ 质量判断（基于 D1-D8 维度的评估）
- 质量判断产出结构化评价：每个维度给出 pass / partial / fail + 具体证据
- 如果 partial 或 fail，产出结构化批评反馈（不是"第 3 节很弱"，而是"第 3 节声称 X 但只提供了 Y 的证据，缺口是 Z"）
- 将质量评估结果写入 `.worktree/verify/quality-assessment.json`

**预期效果：** 实现 evaluator-optimizer 环路，让文档在交付前经过实质性质量评审，不只是清单打勾。

### 变更 4：增加材料角色分类，增强 intake 和 evidence

**为什么排第四：** 当前系统把所有输入材料一视同仁。模板被当数据源摘要，需求文档被当背景材料参考，权威数据被当普通信息引用。这直接导致产出文档的 source fidelity 和 factual accuracy 出问题。

**具体做法：**
- 在 document-intake SKILL.md 中增加材料分类步骤（约 10-15 行）
- 分类两个轴：权威等级（约束性 / 权威性 / 参考性 / 示例性）× 提取方式（保留 / 转化 / 模板 / 过滤）
- 在 manifest.json 中为每个源标注角色
- 在 document-evidence SKILL.md 中根据角色差异化提取：从约束性来源提取硬需求，从权威来源提取事实，从示例来源提取结构模式

**预期效果：** 系统不再混淆模板和数据源，不再把参考材料和权威材料等权处理。

### 变更 5：增加自适应流水线深度

**为什么排第五：** 当前系统强制所有任务走 intake → reader → merger → planner → writer → verifier 六步。一个"帮我总结这封邮件"的任务不需要 6 个子代理。过度流程化反而消耗上下文、增加出错机会、降低响应速度。

**具体做法：**
- 在 using-document-workflows SKILL.md 或 common-work.md 中增加任务复杂度评估（约 15-20 行）
- 三级深度：
  - **轻量**（单源、类型明确、短输出）：意图重建 → 直接起草 → 快速验证
  - **中等**（少量源、类型明确、中等输出）：意图重建 → intake → evidence → compose → verify
  - **重度**（多源、类型不明、长输出、多轮修改）：完整流水线 + 迭代
- 评估信号：源文件数量、输出长度预期、类型清晰度、是否有模板/结构参照

**预期效果：** 简单任务快速出结果，复杂任务才启用重型编排，用户体验和资源效率同时提升。

## 七、两条轴如何合起来

这是本次综合分析最核心的结论。

Track A（文档基础能力）回答的是：**系统应该具备什么样的"文档智力"。**
Track B（Harness Engineering）回答的是：**如何设计外部结构让这些"文档智力"在实际运行中稳定发挥。**

两者缺一不可：

- 只有 Track A 没有 Track B = 系统"知道什么叫好"但"做不到好"
- 只有 Track B 没有 Track A = 系统"运行很稳"但"不知道往哪个方向好"
- 两者结合 = 系统既有内在标准，又被放在一个"做对更容易、做错更难"的环境里

**最关键的交叉点：**

| Track A 的能力 | Track B 提供的 Harness | 交叉产出 |
|---------------|----------------------|---------|
| 8 个质量维度 | 评价器-优化器环路 | 文档在交付前经过实质性质量评审 |
| 任务意图重建 | 任务建模 harness + index.json schema 扩展 | 模糊指令被转化为结构化内部目标 |
| 材料角色分类 | 观察面 harness + manifest schema 扩展 | agent 在正确的权威层级上使用每份材料 |
| 自适应深度 | 场景加载 harness + 条件式 skill 注入 | 简单任务快速，复杂任务严谨 |
| 跨场景泛化 | 三层 skill 架构（核心 / 工作流 / 场景） | 基础层不被场景偏置污染 |

## 九、一个判断标准

从现在开始，我们评价任何设计变更是否值得做，不再问：

- "它是不是更完整"
- "它是不是更优雅"
- "它是不是更像前沿 agent 系统"

**而是问：**

1. **它能不能让文档产出的质量变得更好？**（Track A 视角）
2. **它能不能让 agent 更容易做出正确动作？**（Track B 视角）
3. **它会不会缩小系统能覆盖的文档场景？**（泛化视角）
4. **它会不会制造第二套真相源或浪费上下文？**（工程纪律视角）
5. **不做它，用户会不会感知到差别？**（用户视角）

5 条里答不上来 3 条，就不进主线。
